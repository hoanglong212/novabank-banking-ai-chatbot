# Threat model, safeguards, known limits

**Security status:** This is an educational local demonstration, **not banking-grade**. It must not be hosted publicly, connected to real bank data or used for financial actions.

- Login verifies PBKDF2 hashes for persisted SQLite identities (seven public seeds plus registered customers), then requires purpose-bound email/TOTP MFA before issuing five-minute HS256 access JWTs and rotating refresh credentials. Every authenticated request checks the database session, credential version, five-minute idle and eight-hour absolute deadline. Logout, session revocation, refresh reuse and password reset invalidate the appropriate sessions. Lockouts/history persist in SQLite: five password/MFA failures in 15 minutes lock sign-in for 15 minutes. The full M1 plan still lacks profile editing and authenticated password change with OTP.
- Registration/email verification/recovery use purpose-bound, hashed, single-use tokens and atomic SQLite transactions. Reset expires after 15 minutes; verification after 24 hours. New customers receive a zero-balance account and ledger mapping. Duplicate registration cannot overwrite a pending identity. Persistent fixed-window request/delivery limits reduce abuse but are not production anti-abuse or constant-time guarantees. See [operating instructions and exact limits](ACCOUNT_RECOVERY_VI.md).
- The local `dev_outbox` deliberately stores actionable token links and email OTPs as a fake mailbox, available only via a read-only CLI with explicit DB path, never through HTTP. Anyone who can read that DB can recover accounts, including seeded staff, and use email MFA fallback. Consumed/replaced links/codes are scrubbed; expired values are hidden by the CLI but retained in storage until replacement/consumption. There is no SMTP or real email ownership proof, encrypted outbox, retention job or production account recovery claim.
- TOTP seeds are encrypted with Fernet using `MFA_ENCRYPTION_KEY` or a generated `<DB_PATH>.mfa.key`; back up that key with the DB. TOTP steps cannot be reused. Factor changes require the existing password plus verification and revoke other sessions/pending login challenges. Setup keys stay in memory in the frontend. Losing the encryption key requires email fallback and authenticator re-enrolment.
- Browser access/refresh credentials use per-tab `sessionStorage`, not HttpOnly cookies; same-origin XSS can read them. This is the retained demo model, not production OAuth/session assurance. Background polling/refresh do not extend idle expiry. Input sends a throttled activity request; client input does not prove a human is present. Server deadlines are independently enforced. Device notices use peer IP plus bounded user-agent as a heuristic.
- A random per-process JWT signing key invalidates access JWTs and pending email codes after restart. Unexpired persisted refresh credentials can still rotate into new access JWTs. Use a stable secret for predictable restart behavior; no signing key is committed.
- Do not enter any real customer PII, API keys, OTP, PINs or payment information. The fabricated bank, balances, transactions and FAQ are synthetic.
- All conversation/message read and delete routes check owner ID derived from the verified demo JWT, not just conversation ID. Transfer confirmation and OTP routes also require the draft's owner.
- `PolicyGateway` performs independent policy authorization; the LLM is not entrusted with decisions. Local allowlist + JSON schemas + owner checks are enforced even when the model chooses an inappropriate tool.
- Remote adapter is **only a proposed contract**: POST `{GATEWAY_URL}/authorize` with `principal_id`, `conversation_id`, `tool_name`, `arguments`; response `{"decision":"ALLOW"}` or `{"decision":"DENY"}`. A real gateway will require stronger authentication, action context, intent/grant and verified execution controls. Unauthorized remote calls fail closed.
- The gateway still cannot reliably infer whether every syntactically valid, resource-authorised call matches the original user intent. The demo checks resource ownership and tool permissions; it does not solve semantic task intent, sequence authorization or data-flow taint.
- FAQ tool results are synthetic and may be controlled differently in a real system. No protection against arbitrary malicious internet content or exfiltration through generated final text has been proven.
- Frontend makes separate standard JSON requests; streaming/SSE is not implemented in this version. User message may remain in DB if Ollama subsequently fails; UI displays explicit error.
- SQLite remains the local store. Confirmation serializes OTP checks, rules, posting and idempotency receipts with `BEGIN IMMEDIATE`; simultaneous transfer/retry tests pass on real temporary SQLite files. This is not load testing or PostgreSQL evidence. Automated backups, whole-database encryption-at-rest and a multi-instance rate-limit strategy still need implementation.
- Tool-event arguments might include data users input; audit log is mock-only and is not security-hardened. A real audit system must minimize/redact sensitive fields, control retention and protect integrity.
- Do not use `mock` tests to claim the LLM can withstand prompt injection. Run controlled tests with a real model and compromised-agent scenario.

- Banking ledger entries and completed history have immutability triggers, including replacement guards. A DB administrator able to drop triggers can bypass them. Reconciliation detects cached-balance drift and malformed journals; it does not repair historical evidence. Existing balances are imported once as opening entries, not reconstructed from demo history.
- Drafts expire after five minutes. Every transfer still uses a simulated SMS OTP displayed to the user, valid at most two minutes with three attempts. The demo OTP hash and delivery are not production MFA; resend/recipient-lookup rate limiting remains missing.
- Transfers use user-scoped confirmation keys to return original receipts after retries. Keys contain no OTP; they are kept in the UI only until the form closes. Full browser refresh/recovery, interbank settlement/reversal and a periodic reconciliation worker are not implemented.
- VietQR bank-list/image services remain external dependencies, despite the PDF's proposed fully simulated QR scope. No real money is sent by the transfer service.
- Transaction details/PDF downloads and notification read updates require ownership. Financial staff reads require explicit permissions; support is excluded. Transfer notifications and recorded balances are committed in the same transaction as posting, so retries cannot duplicate them and storage failure rolls them back. Notification Center polls while visible; there is no SSE transport.
- Migration v2 preserves old financial history; only a known v1 payer success audit can supply an old balance snapshot. Older recipient/seed balances stay unknown. These receipts are simulated, not legal bank statements. Server-side PDF escaping prevents markup injection; the PDF route sets `Cache-Control: no-store`.
- The local dependency audit on 1 November reports two moderate development-tool advisories (`vite` 6.4.4 and `postcss-selector-parser` <6.1.5). They remain pending a separate compatible dependency update; adding Playwright does not establish a clean security audit. No dependency security scanner is configured in CI yet.
